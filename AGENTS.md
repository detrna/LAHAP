## Key Mathematical Formulas

1. **Daily Production (ToCook):**
   $$\text{TotalPortions}(P, M, D, W) = \sum [\text{order.slot} \mid \text{Success} \land \neg\text{Skipped}]$$
   $$\text{IngredientRequirement}(B, D, W) = \sum_M (\text{TotalPortions}(M) \times \text{QuantityPerPortion}(B, M))$$
2. **Stock Shortage:**
   $$\text{NeedsPurchase}(B) = \max(0, \text{WeeklyRequirement}(B) - \text{CurrentStock}(B))$$
3. **Allergen Clash:**
   $$\text{IsClash} = (\text{UserAllergies} \cap \text{MenuAllergenTags}) \ne \emptyset$$
4. **Order Total (BR-17/18):** `Total = slots × price − tierDiscount − promoDiscount + deliveredSlots × feePerSlot`. Tier is applied first, then promo on the reduced food subtotal. If `promoCode.allowStackWithTier = false`, apply only `max(tier, promo)`. Delivery fees are **never** discounted. **Snapshot the whole breakdown on `Subscription` at checkout** (decided 2026-11-02): `pricePerPortion`, `foodSubtotal`, `tierId` + `tierDiscount`, `promoDiscount`, `deliveryFeePerSlot`, `deliveryFeeTotal`, and `totalPrice` (must equal `foodSubtotal − tierDiscount − promoDiscount + deliveryFeeTotal`). Income reports (UC-31) sum these from `Success` orders, plus `DELIVERY_SERVICE_UPGRADE` payments in the period of `paidAt` and minus confirmed `DeliveryMethodChange` refunds in the period of `refundedAt`, and skips never change them (BR-11).
5. **Delivery Fee (BR-15):** `km = ceil(getDistanceInKm(business, orderPin))`; fee = `0` if `km ≤ freeRadius`, else `(km − freeRadius) × pricePerKm`. Beyond max distance, hide the delivery option (do not reject). The kitchen location is on `Business`. Each parameter resolves as `package.<param> ?? business.<param>`. Snapshot the fee into the order at checkout, because rate changes only apply to new orders (BR-16). `getDistanceInKm` in `backend/src/shared/utils/distance/` returns **unrounded** km, so callers apply `ceil`.
6. **Churn (BR-28):** has a `Success` history ∧ no active order ∧ `MAX(endDate) < today − 14 days`. Only `Success` subscriptions count and only the latest `endDate` matters (an active or upcoming paid order has `endDate ≥ today`, so it covers "no active order"; a `Pending` order doesn't save a customer from churn). The churn list and the follow-up also require an active `CUSTOMER` account.
7. **Cut-off (BR-09):** order and cancel allowed until 23:59:59 the day before the first service day, in `Asia/Jakarta`.

## Backend Conventions

### Layout (ports & adapters)

| Concern | Location & naming |
| :--- | :--- |
| Port (interface) | `src/shared/ports/<name>/<name>.ts` exporting an interface + I/O types, with `export * from "./errors.js"` at the top |
| Port errors | `src/shared/ports/<name>/errors.ts` |
| Adapter | `src/infrastructure/<port-name>/<vendor>/<vendor>.ts`, class `<Vendor><PortName> implements <PortName>` (e.g. `MidtransPaymentGateway`, `QwenStockLevelEstimator`). Async setup uses a `load<Thing>()` factory |
| Shared vendor client | `src/infrastructure/<vendor>/` (e.g. `infrastructure/qwen/` shared by both Qwen adapters) |
| Config | `src/config/<name>.ts` exports `<name>EnvSchema` (Zod), `type <Name>Env`, a `readonly` `<Name>Config` interface with **UPPER_SNAKE** keys, `to<Name>Config(env)`, `load<Name>Config(env)` |
| Wiring | Register new config in `config/index.ts` (`Config`, `envSchema`, `loadConfig`), new adapters in `infrastructure/index.ts` (`Adapters`, `createAdapters`). `Adapters` holds adapter instances typed by their ports, and is distinct from the `infrastructure/` folder, which also holds non-port code (`db.ts`, migrations, BullMQ). `db` is deliberately **not** in `Adapters`, so only repository adapters can reach it, and new env vars in `backend/.env.example` |
| Pure helpers | `src/shared/utils/<name>/` with their own `errors.ts` (`decimal/` has `roundHalfUp`). **Shared helpers** (decided 2026-11-05): time in `src/shared/time/` (`timestamp.ts`: `toDbTimestamp`/`toIsoTimestamp`/`fromIsoTimestamp`; `schemas.ts`: `isoTimestampSchema` (offset required) and `isoDateSchema` → `PlainDate`; `calendar.ts`: `startOfWeek`, `nextMonday`, `startOfMonth`/`endOfMonth`, `daysBetween`, `isMonday`, `isFirstOfMonth`; `date-range.ts`: `resolveDateRange(input, { defaultFrom, defaultSpanDays, maxDays })`, whose defaults come from the service's clock; `indonesian-date.ts`: `formatIndonesianDate(date, "short-weekday" | "long")` for `Senin, 9 Nov` and `12 Oktober 2026`, used by the delivery obstacle notification and meant for retention's `{tanggal_berakhir}`); meal times in `src/shared/utils/meal-time/` (`clockTimeSchema` for `HH:mm` input, `toDbTime`, `isSameClockTime` at minute precision); request Zod helpers in **`src/shared/schema/`** (same name as the modules' `schema/`): `queryBooleanSchema`, `searchQuerySchema`, `uniqueArray(item, { by? })`, `decimalSchema({ scale, min?, max?, exclusiveMin? })`, `latitudeSchema`/`longitudeSchema` + `refineCoordinatesTogether` (create: both or neither, `null` counts as missing) and `refineCoordinatesPatch` (updates: both sent or both missing, both `null` to clear), `passwordSchema` (8–72 characters and at most 72 bytes), `photoKeySchema` and `photoKeyIn(folder)` (a key inside that folder, no empty, `.` or `..` segments); photos in `src/shared/media/photo.ts` (`PHOTO_FOLDERS`/`PhotoFolder`, `toPhotoUrl`, `toPhotoUrls`, which signs each distinct key once) |
| Domain modules | `src/modules/<module>/` (decided 2026-11-03, plural names), **one folder per layer, with a class file + one file per method** (Go-style receivers; see the block below the table): `controller/<module>.controller.ts`: class `<X>Controller` (HTTP only: validated input → service → `createSuccessResponse`), with handlers in `controller/<action>.ts`. `service/<module>.service.ts`: class `<X>Service` (use cases and business rules; UML anemic domain, so the logic lives here), with methods in `service/<action>.ts`. `service/interfaces/<module>.repository.ts`: the repository **port the service owns** (interface `<X>Repository` + record types, re-exports the domain errors). `repository/prisma/<module>-repository.ts`: class `Prisma<X>Repository implements <X>Repository`, with methods in `repository/prisma/<action>.ts`. `domain/`: `errors.ts` (single file) and `<entity>.domain.ts`, which holds the module's **response types mirroring the `openapi.json` schemas** (decided 2026-11-03: one `readonly` interface per schema with the same name, nullable = `T | null`, not required = `foo?: T | undefined`, dates as ISO strings; enum schemas as `<NAME>S` const arrays + a type, like `ROLES`) plus pure rules. Request schemas (`*Create`, `*Update`, `*Request`) are not domain types; they go in `schema/` as Zod. Another module's domain types may be imported with `import type` only. Shared shapes live in `shared/` (`Role`, `MealTimeView`, `BatchDeleteResult`/`BulkUpdateResult`). `routes/<module>.routes.ts` (single file): `create<X>Router({ controller, tokenProvider })`, where each endpoint chains authenticate → authorize(`x-roles`) → validate → `controller.<handler>`. `schema/<module>.schemas.ts`: Zod request schemas mirroring `openapi.json`. `container/<module>.container.ts`: class `<X>Container({ db, adapters, http, …otherServices })` (`ModuleDeps` in `src/modules/module-deps.ts`) builds repository → service → controller → router, exposes `service` + `router`, wiring only. The container is the only place that sees the whole `adapters` object: it hands services and routers **individual ports** (`new UsersService(repo, adapters.hasher)`), never `adapters` itself. **Dependency rule:** `service/` and `domain/` never import `repository/prisma/`, Prisma, Express or `infrastructure/`. Only the container (the composition root) imports the adapter, and the adapter imports the port (outer → inner). Tests sit next to each method file. A module with many methods groups each layer's method files into one subfolder per entity, keeping the class files at the layer root (decided 2026-11-06 for `catalog`: `service/allergies/get-allergies-by-ids.ts`, `repository/prisma/allergies/…`). **Interfaces only at boundaries:** the repository port, plus **cross-module** dependencies, which are declared by the *consuming* module in `service/interfaces/` (e.g. orders declares `TierDiscountProvider`, and `TiersService` satisfies it structurally). No interface between controller and service; tests mock the class type (`Pick<UsersService, "getById">`), which works because dependencies are `readonly`, not `private`. `createModules` (`src/modules/create-modules.ts`, used by `app.ts` and the worker) creates containers in dependency order, passes **services** (never repositories) across modules, creates shared singletons once and passes them in, and mounts each `router` on the `/api` router. **Where pure rules live (decided 2026-11-03):** a rule only one module uses goes in that module's `domain/` as its own file + test (`modules/orders/domain/order-total.ts`, `cut-off.ts`, `delivery-fee.ts`; `modules/catalog/domain/package-availability.ts`). It moves to `src/shared/utils/<name>/` only when a second module needs it, because other modules may only `import type` from a module's domain. Shared today: `phone`, `meal-time`, `distance`, `message-template`, `churn` (`CHURN_AFTER_DAYS`, `churnCutoffDate`, `isChurned(lastSuccessEndDate, today)`; created by users, reused by retention), `ingredient-requirements` (`sumIngredientRequirements(portionsByMenu, recipeLines)`, formulas 1–2 summed per ingredient and rounded half up to 2 decimals; created by the ingredients shopping list, put in `shared/` before a second user as a deliberate exception because kitchen's to-cook needs it). **Module boundaries (decided 2026-11-03):** each table has exactly one owning module, and only that module's service writes it. Another module's data, read or write, goes through **its service** behind an interface the consumer declares. A repository never crosses modules, not even through a join on its own link table (decided 2026-11-06): `users` stores only `user_allergy` ids and gets the allergies from `CatalogService`, its membership from `TiersService` and the last paid end dates for churn from `OrdersService`. Read models follow the same rule (decided 2026-11-06): kitchen to-cook, the courier list, reports, announcement recipients and admin lists get other modules' data from those modules' services and join it in memory. To filter by another module's field, ask the owner for the matching ids, then filter your own table by them (like users' `churned` filter). Providers expose batched methods (`getXByIds(ids)`), so a list makes one call per page, never one per row. When the provider is created later in `app.ts`, the consumer gets a closure object over the provider's service (users → auth `SessionRevoker`, catalog → ingredients), and until the provider's method is built, the consumer's interface file exports a no-op (`noOrderActivity`) that is correct while the provider has no data. ### Errors

- **Where errors live** (decided 2026-11-05): an error several modules use goes in `src/shared/errors/`; an error only one module throws stays in that module's `domain/errors.ts`. Shared today: `AppError`, `ValidationError` (400 `VALIDATION_ERROR` with `issues`; `RequestValidationError` and `InvalidDateRangeError` extend it, and `errorHandler` returns the issues for any of them), `InvalidStateError` (422 `INVALID_STATE`), `OrderNotFoundError` (404 `ORDER_NOT_FOUND`, thrown by orders and delivery), `UserNotFoundError` (404 `USER_NOT_FOUND`, thrown by users and retention) and `UnknownAllergyError` (400 `UNKNOWN_ALLERGY`, thrown by users and ingredients). Throw `new InvalidStateError("cut-off has passed")` for every business-rule or state violation, with a specific lowercase message, rather than a new class per case.
- Every domain or infra error extends `AppError` (`src/shared/errors/app-error.ts`) with `readonly code` (UPPER_SNAKE string) and `readonly statusCode` (HTTP status).
- Name classes with an `…Error` suffix (`InvalidHashInputError`).
- Messages are lowercase and do not end with a period. Always pass `{ cause }` when wrapping.
- Adapters must translate vendor exceptions into port errors (`…ProviderError` = 502, `…FailureError(operation, cause)` = 500). Never leak vendor errors.
- Constructor misconfiguration throws a plain `Error("<ENV_VAR> is not set")` (fail fast at boot).

### HTTP

- Responses use the envelope helpers in `src/shared/response/`: `createSuccessResponse(data, meta?)` gives `{ data, meta? }`, `createPaginatedResponse(items, {page,limit,total})` gives `{ data, meta: PaginationMeta }`, and errors come out as `{ error: { code, message, issues? } }` (produced only by `errorHandler`).
- Middleware is a factory that takes a deps/options object (`authenticate({ tokenProvider })`, `errorHandler({ logger })`). App-level order in `app.ts`: `trust proxy` setting → `requestLogger` → `helmet` → `corsPolicy` → `express.json` → `/health` → `storageProxy` → routers → `errorHandler` (last). Route chain order: `authenticate → authorize(...roles) → rateLimit → uploadImage → validateRequest/validateBody/... → paginate() → handler` (skip the ones a route doesn't need).
- **HTTP foundation** (decided 2026-11-03; settings in `config/http.ts`, reached through `ModuleDeps.http`):
  - `requestLogger({ logger })`: `req.id` from a safe incoming `X-Request-Id`, otherwise a UUID, echoed in the response header. It logs one `request completed` line per request (`requestId, method, path, statusCode, durationMs, userId?`). The path is logged without the query string, so tokens never reach the logs, and `/health` is skipped. `errorHandler` adds `requestId` to its logs.
  - `corsPolicy({ origins })`: allows `CORS_ORIGINS` (exact origins, comma-separated) **with credentials** (needed for the refresh cookie; never use `*`), and exposes `X-Request-Id` and `Retry-After`. Set `TRUST_PROXY` when deployed behind a reverse proxy, so `req.ip` is the client.
  - `uploadImage({ field, maxBytes: http.UPLOAD_MAX_BYTES })` (multer, memory storage): one JPEG, PNG or WebP per request. The type is detected from the file's magic bytes, and `req.file.mimetype` is overwritten with it. Failures: missing file → 400 `VALIDATION_ERROR`, too large → 413 `PAYLOAD_TOO_LARGE`, other types → 415 `UNSUPPORTED_MEDIA_TYPE`. Used by `POST /files` (`field: "file"`) and the photo estimate (`field: "image"`). Put `validateBody` after it for the text fields.
  - `rateLimit({ cache, logger, name, limit, windowSeconds, key? })`: a fixed window per client IP, on `Cache.increment`. Over the limit it sets `Retry-After` and returns 429 `TOO_MANY_REQUESTS`. When Redis fails it lets the request through and logs a warning. Applied to `POST /auth/login` and `POST /auth/register` with `AUTH_RATE_LIMIT_MAX`/`AUTH_RATE_LIMIT_WINDOW_SECONDS` (default 10 per 60 s).
- **Realtime** (decided 2026-11-06, built the same day): realtime is plain transport, and its only public method is `RealtimeService.publish(audience: { userIds?, roles? }, event)`. **The publisher chooses the recipients** (it knows the slot's customer and courier); modules declare `RealtimePublisher { publish(audience, event) }` in their own `service/interfaces/` and get `realtime.service`. **Every event goes through Redis pub/sub**, through the `EventBus` port (`shared/ports/event-bus/`, adapter `infrastructure/event-bus/redis/`, `adapters.eventBus`), because the worker is a separate process that holds no connections: each API process subscribes once at startup and delivers to its own streams, so several API instances work. The adapter prefixes channels with `KEY_PREFIX` itself (ioredis's `keyPrefix` only covers keys) and uses two connections (a subscribed one can't publish). A Redis outage loses events (no replay; clients refetch after reconnecting), and a failed `publish` is logged and rethrown, so callers treat it as best-effort. The stream sends `retry: 5000` first and a `: ping` every `REALTIME_PING_INTERVAL_SECONDS` (25). **It closes at the access token's `exp`** (the client refreshes and reconnects, so a deactivated user loses the stream within `JWT_EXPIRES_IN`), keeps at most `REALTIME_MAX_CONNECTIONS_PER_USER` (5, the oldest is closed) streams per user, answers 503 `SERVICE_UNAVAILABLE` past `REALTIME_MAX_CONNECTIONS` (1000) per process, and closes a client whose unsent buffer passes 1 MB. All three settings are in `config/http.ts`. `authenticate({ tokenProvider, allowQueryToken: true })` also reads `?accessToken=`, and **only the stream route sets it**, so no other route accepts a token in the URL. **`createApp` returns `{ app, start, close }`**: `index.ts` awaits `start()` (subscribes) before `listen`, and shuts down with `close()` (ends every stream, because `server.close()` waits for them) → `server.close()` → database, cache and `adapters.eventBus`. The worker builds the same adapters (`createAdapters`, with its own logger) and modules (`createModules` in `src/modules/create-modules.ts`, which `createApp` also uses), never calls `realtime.service.start()`, so its realtime service only publishes, and closes the database, cache and event bus on shutdown. `createTestApp` opens a bus under its random prefix unless `adapters.eventBus` is given.
- Never write error responses yourself. Async route handlers just `throw` (or let promises reject): Express 5 forwards that to `errorHandler`. Middleware forwards failures with `next(err)`.
- **Request schemas reuse the shared helpers** (`src/shared/schema/`, `shared/time/schemas.ts`, `clockTimeSchema`): boolean query filters use `queryBooleanSchema`, **never `z.coerce.boolean()`** (it turns `"false"` into `true`); `?search=` uses `searchQuerySchema` (an empty value means no filter); dates use `isoDateSchema`, timestamps `isoTimestampSchema`, meal times `clockTimeSchema`; money, distances and percentages use `decimalSchema` with the column's scale and limits (e.g. `Numeric(5, 2)` → `max: 999.99`), so out-of-range input is a 400 rather than a database 500; id lists use `uniqueArray(z.uuid())`.
- Validated, coerced input replaces `req.body/query/params`. `req.user = { userId, name, role }` and `req.pagination = { page, limit, offset, skip, take }`.
- **Auth sessions (decided 2026-11-02, refresh tokens stored 2026-11-04): JWT pair, stateless access token, stored refresh token.** Register/login return `{ accessToken, refreshToken, tokenType: "Bearer", expiresIn, refreshExpiresIn, user }` (`JwtTokenProvider.signTokenPair`, whose `refreshTokenId` is the refresh token's `jti`). Access tokens are never stored or looked up (they stay valid until they expire). Every issued refresh token gets a `refresh_token` row (`id` = `jti`, `expiresAt`, `revokedAt`), owned by `auth` (`AuthRepository`). `POST /auth/refresh` **rotates**: it revokes the presented token with a conditional update (`revokedAt IS NULL`, so two concurrent refreshes can't both win), re-checks the user still exists and `isActive`, and issues a new pair. A token that is stored but already revoked counts as **reuse** (likely theft): every active token of that user is revoked and 401 `INVALID_TOKEN` (`refresh token has been revoked`). Two tabs refreshing with the same token at once can trigger it. A token with no row (unknown `jti`) is just 401. `POST /auth/logout` is **public** (no access token, so it works after the access token expired): it revokes the refresh token from the body or cookie and always answers 204, also with no token, an invalid or expired one, or one that is already revoked (logout never triggers reuse detection). There's no "log out everywhere" endpoint yet. **Session revocation (decided 2026-11-05):** `AuthService.revokeSessionsOfUser(userId)` revokes every active refresh token of a user. `users` calls it through its own `SessionRevoker` interface after a password change (`PUT /me/password`, including the current session), an admin password reset and a deactivation. Because `users` is created before `auth`, `app.ts` passes `users` a closure that calls `auth.service` later. Expired rows are never cleaned up yet (a worker job can delete by `expiresAt` later).
- **Refresh cookie (decided 2026-11-04):** register, login and refresh also set the refresh token as an `HttpOnly` cookie (`AUTH_COOKIE_NAME`, default `lahap_refresh`; `Path=/api/auth`; `Max-Age` = `refreshExpiresIn`), and logout clears it with the same attributes (`controller/refresh-cookie.ts`). The frontend and backend run on **different sites**, so production uses `AUTH_COOKIE_SAME_SITE=none` + `AUTH_COOKIE_SECURE=true` (config refuses `none` without `Secure`); local development uses `lax`/`false`. The refresh token **also stays in the response body** (decided 2026-11-04: sending it in the body is standard for OAuth and native clients), and `/auth/refresh` and `/auth/logout` read the body first, then the cookie (`readRefreshToken`; `cookieParser()` on those two routes only). Refresh answers 401 `MISSING_TOKEN` when neither is sent. Browsers should rely on the cookie (`credentials: "include"`) and keep only the access token in memory. Cross-site cookies can be blocked by Safari and third-party-cookie restrictions; the body token is the fallback. A leaked refresh token works only until it or its successor is used again (reuse detection) or the user logs out; otherwise it expires after `JWT_REFRESH_EXPIRES_IN` (7d).
- **Auth implementation** (decided 2026-11-03):
  - Each token carries `typ` (`access`/`refresh`), checked on verify. `JwtTokenProvider` refuses to start when `JWT_SECRET` equals `JWT_REFRESH_SECRET`. `TokenPair.expiresIn` and `refreshExpiresIn` are the access and refresh tokens' lifetimes in seconds.
  - `users` owns passwords: `UsersService.createUser`/`registerCustomer`/`verifyCredentials`/`getActiveById` hash and compare through the `Hasher`, and the hash never leaves the module. `createUser` (role + `isActive`, used by `POST /admin/users`) holds the registration logic; `registerCustomer` wraps it with `CUSTOMER`/active. `auth` reaches them through its own `UserAccounts` interface, and `app.ts` creates `users` before `auth`.
  - Login gives the same 401 `INVALID_CREDENTIALS` for an unknown user, a wrong password, an inactive account and an unparseable identifier, and runs one bcrypt compare (against a dummy hash) even when the user doesn't exist. An identifier containing `@` is an email (lowercased); anything else goes through `normalizePhone`.
  - Register: 409 `CONFLICT` (`phone is already registered` / `email …`, including concurrent sign-ups that hit the unique constraint), 400 `UNKNOWN_ALLERGY` for ids not in the allergy list. Request bodies use `phoneSchema`, and passwords are 8–72 characters **and** at most 72 bytes (bcrypt's limit).
  - `AuthSession.user` is `User` with `allergies` and without `membership`/`isChurned`; `/me` returns the full profile.
- **Media (decided 2026-11-02): no File table.** `POST /files` (multipart) uploads through `ObjectStorage` and returns `{ key, url }`. Clients send the `key` as `photoKey` when creating or updating an entity. Every response exposes `photoUrl = getSignedUrl(photoKey)`, signed fresh on each read, because the adapter only issues expiring signed URLs (`S3_SIGNED_URL_EXPIRES_IN`). Never store URLs. **Photo URLs go through the API (decided 2026-11-09):** the adapter talks to SeaweedFS on `S3_ENDPOINT` (internal) but signs URLs with a second client on `S3_PUBLIC_ENDPOINT` (an origin without a path; defaults to `S3_ENDPOINT`), so production links look like `https://lahap.bccdev.id/<bucket>/<key>?X-Amz-…`. The `storageProxy` middleware (`app.ts`, after `/health`, before `/api`) takes only `GET`/`HEAD` requests under `/<bucket>/` that carry `X-Amz-Signature` and hands them to `ObjectStorage.forwardSignedRead`, which sends the same path and query to `S3_ENDPOINT` with `Host` set to the public host, so SeaweedFS checks the signature and expiry itself. It forwards only `Range`/`If-None-Match`/`If-Modified-Since`, returns only content headers plus `Cross-Origin-Resource-Policy: cross-origin` (helmet's default `same-origin` would stop the frontend's other origin from showing the images), and anything else falls through to the routers. This exists because the VPS can't reach the bccdev proxy's public address, so pointing `S3_ENDPOINT` at a public name crash-loops the API at its startup bucket check. Uploads that are never attached stay in the bucket (acceptable for the MVP). **Upload rules (decided 2026-11-05):** keys are `<folder>/<YYYY>/<MM>/<uuid>.<jpg|png|webp>` (Asia/Jakarta month, extension from the detected type; seeded rows use `<folder>/seed/<id>.webp`). `POST /files` is `ADMIN` (any folder) and `COURIER` (`obstacles` only, otherwise 403 `FORBIDDEN`). KITCHEN has no endpoint that takes a `photoKey`; the photo estimate uploads its own `image` and stores nothing. When an entity gets a new `photoKey`, its request schema uses `photoKeyIn("<folder>")`, and its service calls `FilesService.assertPhotoKeyExists(key, path?)` through a `PhotoKeys` interface it declares (400 `VALIDATION_ERROR`, issue code `photo_not_found`). Skip the existence check when the key equals the stored one, because a stored key may point at an object that's gone (a bucket that was emptied or never seeded).
- The API prefix is `/api/...`. **`docs/api/openapi.json` supersedes the USE_CASES §5 route map** (decided 2026-11-02). Its conventions:
  - Paths use the code's model names: `/subscriptions` = PRD "Pesanan", `/orders` = slots. Role areas are `/kitchen/*`, `/courier/*` and `/admin/*`; the signed-in user is `/me/*`; public catalog routes are `/packages`, `/allergies`, `/tiers` and `/business`.
  - Each operation lists its allowed roles in `x-roles`.
  - Status codes: 409 for uniqueness or "still referenced" conflicts; **422 `INVALID_STATE`** for business-rule or state violations (cut-off passed, wrong slot status, unavailable package); 404 also for other users' resources.
  - Checkout (`POST /subscriptions`, with `/subscriptions/preview` for the dry run) takes `menuScheduleIds` for `Harian`, or `periodStart` + `deliveryTimes` for `Mingguan`/`Bulanan`.
  - An invalid promo code never fails the request; it comes back in `preview.promo.reason`.
  - Bulk endpoints (`/admin/courier-assignments`, `/admin/menu-schedules/publish`, `/kitchen/food-ready`) accept explicit ids **or** a group (date + meal time, package + date range, schedule). The data is still written per row.
  - Realtime is one SSE stream, `GET /api/realtime/stream`, with events `slot.status`, `slot.obstacle`, `slot.menu`, `notification` and `announcement`. Because `EventSource` can't send headers, it also accepts `?accessToken=`.

### Time (decided 2026-11-03)

- **Never read the system clock in services or domain code** (`Temporal.Now`, `new Date()`, `Date.now()`). Tests use `createFixedClock(...)`.
- **Domain `Timestamp` columns store UTC wall-clock time** (`Temporal.PlainDateTime`), because that's what Prisma's `@onCreate(now())`/`@onUpdate(now())` write. When writing a timestamp yourself, use `toDbTimestamp(clock.now())` from `src/shared/time/timestamp.ts`. `Date` columns are business dates: "today" is `clock.now().toPlainDate()`. `JobRun` keeps `TimestamptzJsDate` (infra-only, absolute instants).
- **Responses render timestamps in Asia/Jakarta with the offset and milliseconds** (decided 2026-11-03): `toIsoTimestamp(row.createdAt)` gives `2026-11-03T08:00:00.000+07:00`. Never send a raw `PlainDateTime`. Factory examples use the same form.

## Domain Quick Reference

- **Roles:** Customer, Admin (owner), Kitchen, Courier. One `/login` page with role-based redirect. **Stored values** (decided 2026-11-02): `CUSTOMER`, `ADMIN`, `KITCHEN`, `COURIER` (UPPER_SNAKE, case-sensitive). Use `ROLES`/`Role`/`isRole` from `src/shared/auth/roles.ts`. The token port, the JWT adapter (`z.enum(ROLES)`, so unknown roles are rejected) and `authorize(...roles: Role[])` are all typed with it. Tests use only these four. **Last-admin guard** (decided 2026-11-05): `PATCH /admin/users/{id}` refuses (422 `INVALID_STATE`) a change that would leave no active `ADMIN`. The users repository locks the active admin rows (`forUpdate()`) inside the update transaction, so two admins can't demote each other at once. Changing a courier's role leaves their slots' `courierId` as is (the admin reassigns them).
- **Terminology trap:** in the PRD, **"Pesanan"/order means the `Subscription` entity** (it carries `Pending`/`Success`/`Expire`/`Dibatalkan`), while **"Slot" is the `Order` model**. "Jadwal Menu"/`MenuSchedule` (UML) is the `Schedule` model. So rules worded "pesanan …" (BR-13, BR-21, BR-22) apply to `subscription`, not to the `order` table.
- **Slot = 1 `Order` row = 1 portion = 1 delivery**, unique `(subscriptionId, menuScheduleId)`. Each slot carries its own `order.isDelivery` and `order.deliveryFee` (copied from `subscription` at checkout, and updated per date range by `DeliveryMethodChange`), while `subscription.isDelivery` reflects the order's current method from the latest applied switch (BR-13).
- **Allergy note & skip reason** (decided 2026-11-02): `user.allergyNote` holds free-text allergies outside the list (UC-41). It can't be matched to menu tags, so **any customer with a non-empty note has all their slots shown in the kitchen's special category** (UC-39), alongside notes and tag clashes. `order.skipReason` is optional and only set when status becomes `Dilewati` (UC-44). "Skip Hari Ini" writes the same reason to each skipped slot.
- **Churn follow-up templates** (decided 2026-11-02): admin-written templates live in `MessageTemplate` (`name`, `body`). Placeholders are a **fixed map in code**: `MESSAGE_PLACEHOLDERS` in `src/shared/utils/message-template/` (`name` → `{nama}`, `lastPackage` → `{paket_terakhir}`, `endDate` → `{tanggal_berakhir}`, `daysSinceLastOrder` → `{lama_tidak_memesan}`, `promoCode` → `{kode_promo}`). Call `generateMessage(template.body, { name, promoCode, … })`, then URL-encode the result into `https://wa.me/<62…>?text=…`. To add a placeholder, add it to that map, never to the database. **Template rules** (decided 2026-11-07): names are trimmed, 1–100 characters and unique ignoring case (checked in the app, 409 `CONFLICT`; no `@unique`, so two admins saving the same name at once could both pass); bodies are trimmed, 1–2000 characters, and any lowercase `{token}` not in the map is a 400 (`findUnknownPlaceholders`), while other braces (`{Nama}`, `{ }`) are left as text, matching `generateMessage`. Deleting a template never conflicts.
- **Courier assignment** (decided 2026-11-02): the admin assigns a courier **per slot** via `order.courierId`. There are no shift tables. A courier's to-do list (UC-30) is their slots where `courierId = me`, `order.isDelivery`, and status `Diantar` (or earlier, for the day's list). The admin UI may bulk-assign, but the data stays per slot.
- **Registration & identity** (decided 2026-11-02): only `phone` + password are required (UC-01). Normalize `phone` with `normalizePhone()` from `src/shared/utils/phone/` before saving **or** looking it up: digits starting with `62` (`0812…`/`+62812…`/`812…` → `62812…`; anything else is 400 `INVALID_PHONE_NUMBER`). `email` is optional (`String?`, unique), stored trimmed and lowercased. When no name is given, set `name = phone`, so `User.name` and the token's `sub.name` are never empty. Login accepts phone or email (UC-13).
- **Order period** (decided 2026-11-02): `package.periods` (`String[]`) lists the periods a package offers (`"Harian"` | `"Mingguan"` | `"Bulanan"`, at least one), and `subscription.period` is the customer's choice, which must be in that list. There is no `durationDays` on packages. Order length = `subscription.startDate`/`endDate` (first and last slot date, for every period). The package sales window = `package.startAt`/`endAt`.
- **Changing the delivery method** (settled and built 2026-11-07; details in `tmp/plan/delivery-method-change-implementation.md`): a customer or admin can switch the delivery method of a `Success` subscription's `Terjadwal` slots from `effectiveFrom > today` (defaulting to the first switchable slot's date) without cancelling. At most one `Pending` `DeliveryMethodChange` is allowed per subscription at a time (locked with `forUpdate`). `Dilewati` slots never switch (BR-11). **Delivery → pick-up:** switches immediately (`status = "Success"`), sets `order.isDelivery = false`, `order.deliveryFee = 0` and `order.courierId = null` (notifying affected couriers and publishing `slot.status`), updates `subscription.isDelivery = false`, sums the switched slots' `order.deliveryFee` into `change.amount`, and sets `change.needsRefund = amount > 0` (confirmed via `POST /api/admin/delivery-method-changes/:id/confirm-refund`, which sets `needsRefund = false` and `refundedAt = now`). **Pick-up → delivery:** quotes `feePerSlot` at today's package/business rates (`km > maxDistance` is 422 `INVALID_STATE`), requires `paymentMethod` (`MIDTRANS` or `CASH` on `Offline` only) unless `amount = 0`, and when `amount > 0` creates a `Pending` change + `DELIVERY_SERVICE_UPGRADE` payment (`amount = slotCount × feePerSlot`); when `amount = 0` (within the free radius), it applies immediately (`status = "Success"`, `payment = null`). Once the upgrade payment succeeds before cut-off (`effectiveFrom > today`), the linked `Terjadwal` slots switch to `isDelivery = true` and `deliveryFee = feePerSlot`, `subscription.isDelivery = true` and its delivery address/coordinates/distance are updated, and admins are notified to assign a courier; if paid after cut-off (`effectiveFrom <= today`) or after the subscription was cancelled, the payment is `Success` while the change becomes `Expire` with `needsRefund = true`. The subscription's checkout price snapshot (`deliveryFeePerSlot`, `deliveryFeeTotal`, `totalPrice`) never changes; income reports (UC-31) add `Success` upgrade payments in the period of `paidAt` and subtract confirmed `DeliveryMethodChange` refunds in the period of `refundedAt` (`netTotal = total − refunded`).
- **Online/Offline & payment method** (decided 2026-11-02): `subscription.purchaseType` is `"Online"` (gateway only, never cash) or `"Offline"` (gateway or cash), set once at checkout (UC-03). `payment.method` is `"CASH"`, `"MIDTRANS"` (channel not chosen yet), or `"MIDTRANS_<PAYMENT_TYPE>"` once the webhook reports it. There is **no `doneOnline` column**. API responses for payments must include a derived `doneOnline = method !== "CASH"`.
- **Each order has its own recipient and delivery point** (decided 2026-11-02). At checkout, save `recipientName` (always), and `deliveryAddress`, `deliveryLatitude`/`deliveryLongitude` and `deliveryDistanceKm` (required when `isDelivery`) on `Subscription`. `User.address`/`latitude`/`longitude` only **prefill** the checkout form and are never written by checkout. Courier contact uses `user.phone`.
- **Meal times (decided 2026-11-02):** the admin types each package's meal times into `Package.deliveryTimes` (`Time[]`, minute precision). There is no meal-time table. A slot is package + date + meal time: `Schedule.deliveryTime`, unique on `(packageId, date, deliveryTime)` (BR-07). The app must check that the time is in the package's list, and refuse to remove a time that slots of active orders still use (UC-20). One subscription can span several meal times (UC-06, UC-09).
- **Meal-time range label is derived, never stored:** use `toMealTimeView(time)` from `src/shared/utils/meal-time/`, which returns `{ time: "07:00", range: "Pagi" }`. The ranges are Pagi 00:00–10:59, Siang 11:00–15:59, Malam 16:00–23:59. It accepts `"HH:mm[:ss]"` strings or `Temporal.PlainTime`, which is what Prisma returns for `Time` columns (Node ≥ 26.8.2 has `Temporal` built in; the project runs 26.12. Its types come from TypeScript's `esnext` lib, set in both tsconfigs, so never import a polyfill).
- **Status values (decided 2026-11-02): Indonesian/PRD naming, stored verbatim and case-sensitive.** Never use the English variants (`SCHEDULED`, `PENDING`, `ACTIVE`, …) for domain statuses. Infra-only statuses such as `JobRun` (`RUNNING`/`SUCCESS`/`FAILED`) are unaffected.
  | Column | Allowed values |
  | :--- | :--- |
  | `subscription.status` | `Pending`, `Success`, `Expire`, `Dibatalkan` |
  | `payment.status` | `Pending`, `Success`, `Expire`, `Refund` |
  | `delivery_method_change.status` | `Pending`, `Success`, `Expire` |
  | `order.status` (slot) | `Terjadwal`, `Disiapkan`, `Diantar`, `Siap Diambil` (with a space), `Selesai`, `Dilewati` |

  Other enumerated columns (UPPER_SNAKE, decided 2026-11-02): `payment.type` = `SUBSCRIPTION` | `DELIVERY_SERVICE_UPGRADE`; `announcement.scope` = `GLOBAL` | `PACKAGE` | `SCHEDULE`.
- **Subscription lifecycle:** Pending payments expire after 15 min through the worker (BR-20). Only `Success` counts for ToCook, courier lists, revenue, and churn (BR-22). The display labels `Akan Datang`/`Aktif`/`Selesai` are derived from dates.
- **Schedule publication:** `Schedule` (called `MenuSchedule` in UML; FK `order.menuScheduleId`) has **no status column**. Visibility is only `isPublished` (decided 2026-11-02).
- **Slot status flow (BR-23), forward-only:** delivery `Terjadwal → Disiapkan → Diantar → Selesai`; pickup `Terjadwal → Disiapkan → Siap Diambil → Selesai`; skip → `Dilewati` (allowed before food-ready, no refund). Courier obstacles are timestamped **notes + notification, not a status**. Every slot status change must record the actor's `userId` and a timestamp (PRD §9.4).
- **Menus:** 1 primary + at most 1 alternative per schedule (`ScheduleMenu.isPrimary`). `@@unique([scheduleId, isPrimary])` enforces the "at most"; the app must verify a primary exists before setting `schedule.isPublished = true`. `Menu.tags` is `String[]` (Postgres `text[]`, no NULL elements). Allergens are inherited from ingredients (union). A clash warns at checkout but never blocks. The kitchen assigns alternatives manually by setting `order.usesAlternativeMenu = true`. A slot's menu is the schedule's `ScheduleMenu` with `isPrimary = !usesAlternativeMenu`, and ToCook counts primary and alternative portions separately. **Menu components & cook assignments** (UC-34, built 2026-11-08): each menu owns 0 or more sub-dish rows in `MenuComponent` (`id`, `menuId`, `name` trimmed 1–100 chars and case-insensitively unique per menu, optional `cookId` referencing an active `KITCHEN` user with `onDelete: SetNull`). `components` is optional on `POST /api/admin/menus` (defaults to `[]`) and on `PATCH /api/admin/menus/{id}` (replaces the full list in one transaction; `[]` clears them), never requires `changeReason` or sends a `SCHEDULE` announcement (BR-26), and answers 422 `INVALID_STATE` (`cook is not an active kitchen staff`) when any `cookId` is not an active `KITCHEN` user (checked via `CookDirectory`: `filterActiveUserIds` + `getSummaries` from `UsersService`, plus `menu_component_cook_id_fkey` mapped in the repository). Every `Menu` response (`GET`/`POST`/`PATCH /admin/menus*`, schedules, and `ToCookMenu` in `GET /kitchen/to-cook`) includes `components: readonly MenuComponent[]` with `cook: UserSummary | null` hydrated.
- **Loyalty tier = `user.membership`** (decided 2026-11-02): `Membership` is 0..1 per user (`userId` unique) with `tierId`, `startedAt`, `expiresAt = startedAt + tier.durationDays`. **Tier rules (agreed with the PM 2026-11-06):** tiers are earned by cumulative paid service days (`requiredSubscriptionDays`), not by spend; the defaults are Biasa 0 days = 0 %, Silver 30 days = 5 %, Gold 60 days = 10 %, each valid 30 days (`durationDays`); the discount is a percent of the food subtotal, never the delivery fee. Every paid order re-evaluates the tier and restarts the window; a cancellation recalculates the tier without extending it. **When a window runs out, the customer drops one level** (not to the lowest): the lower tier gets a fresh window starting when the old one ended, and at the lowest tier the membership just becomes inactive. This step-down is computed on read by tiers (`effectiveMembership`), never by a job, and the next paid order restores the tier the customer's days earn. The discount comes from the effective tier while it's active, and `getActiveDiscount` answers `null` for a 0 % tier, so `subscription.tierId` is only set when a tier discount was actually given. Re-evaluation updates the row in place (no history), and there is no `User.tierId`. **Counting and re-evaluation** (decided 2026-11-06): `subscriptionDays` is the number of distinct service dates in the customer's slots of `Success` subscriptions (skipped and future paid dates count; `Dibatalkan`, `Expire` and `Pending` don't), counted by orders through `OrderStats.countPaidServiceDays`. 0 paid days means no membership, even with a 0-day tier. `TiersService.reevaluate(userId, { renewWindow })` runs under a per-user Postgres advisory lock (`withUserLock`), after the day count is read: orders calls it after the commit that makes a subscription `Success` (`renewWindow: true`: upsert the earned tier with a new window) or cancels a `Success` one (`renewWindow: false`: only lowers the tier and keeps the dates; it never creates or extends a membership). Both are best-effort, logged on failure. Editing a tier never rewrites memberships (a new threshold applies at each customer's next re-evaluation, a new `durationDays` at their next renewal), and `memberCount` counts effective active memberships. Deleting a tier locks its row (`forUpdate`) before moving or removing members, and always succeeds (no 409). `tiers` is the only writer and reader; `users` gets it for `/me` and the admin user detail from `TiersService.getMembership(userId)` (its `MembershipLookup`), which returns the effective membership (with `isActive`) and signs the badge with `toPhotoUrl`. The admin user list leaves `membership` out.
- **Deleting a tier** (UC-38, decided 2026-11-02): `Membership.tier` blocks deletion while members exist. In one transaction: move its members to the **previous tier** (the highest `requiredSubscriptionDays` below it, which is unique), **keeping `startedAt`/`expiresAt`**. If there's no lower tier, delete those memberships. Then delete the tier. Subscriptions that used it get `tierId = null` and keep `tierDiscount`. Validate UC-36: `requiredSubscriptionDays ≥ 0`, `durationDays > 0`, `0 ≤ discountPercent ≤ 100`.
- **Business (singleton):** exactly one `business` row holds the kitchen location, delivery defaults, `paymentTimeoutMinutes` (BR-20) and `whatsappNumber` (the business contact number, kept for future features; churn `wa.me` links use the customer's number). Read it, don't hardcode these values. The `settings` module owns it (`SettingsService.getSettings()` is the read other modules use; `getBusinessInfo()` is the public subset). **The seed creates the row** and the app never inserts a second one: `PUT /api/admin/settings` replaces every field in the existing row (the oldest, if there were ever two) and creates it only when the table is empty. A read with no row throws 500 `BUSINESS_NOT_CONFIGURED`. Limits are checked in the request schema (`deliveryFreeRadius ≤ deliveryMaxDistance`, `paymentTimeoutMinutes` 1–1440, `whatsappNumber` normalized). Rates and the kitchen location only affect new orders (BR-16), but a new `paymentTimeoutMinutes` also applies to orders already `Pending`, because the expiry worker reads the current value (decided 2026-11-06). Tenant scoping (`business_id` everywhere) is **deferred past the MVP** (decided 2026-11-02); don't add `businessId` columns.
- **Packages:** a package is **active** (derived, never stored) when `isActive && startAt ≤ now && (endAt == null || now < endAt)` (BR-03, UC-22). `isActive` is the admin's reversible manual switch, and `endAt = null` means no expiry. Only active packages appear to customers and accept new orders. Running `Success` orders on an inactive package are still served (kitchen, courier, slots ignore it).
- **Promo codes:** `discountType` is `"Persen"` | `"Nominal"`, and `discountValue` is a percent or Rp accordingly. Enforce `minPurchase` against the food subtotal before discounts. Also check `quota`, `validUntil` and `isActive`. **Each customer can use a code only once** (decided 2026-11-06): the check counts only that customer's `Success` subscriptions with the code, so an abandoned `Pending` order doesn't block a retry. **Quota is a total, not a counter** (decided 2026-11-06): `usedCount` is derived by orders as the `Pending` + `Success` subscriptions with the code (`PROMO_USE_STATUSES`), so an expired or cancelled order gives its use back and nothing is decremented; `quota = 0` means the code can never be used. Codes are stored uppercase (`A–Z`, `0–9`, `-`, `_`, 1–50); lookups uppercase the input. Deleting a code answers 409 while a `Pending` subscription uses it. Orders computes the discount amount and `TIER_DISCOUNT_LARGER`; promo-codes only validates the code.
- **Cancellation & refunds:** cancelling a `Success` subscription sets `status = "Dibatalkan"` and `needsRefund = true` (and expires any `Pending` `DeliveryMethodChange`). The admin refunds outside the app, then confirms (`POST /api/admin/payments/:id/confirm-refund`), which sets that payment's `status = "Refund"` and clears the subscription's `needsRefund = false` once no other `Success` payment on the subscription remains unrefunded. Delivery-to-pickup downgrade refunds and late-paid upgrade refunds are tracked on `DeliveryMethodChange.needsRefund` and confirmed via `POST /api/admin/delivery-method-changes/:id/confirm-refund` (`needsRefund = false`, `refundedAt = now`).
- **Orders decisions (settled and built 2026-11-06; details in `tmp/plan/orders-implementation.md` "Decisions settled"):** **Gateway mapping:** `PAID → Success`, `PENDING → Pending`, `EXPIRED → Expire`; `CHALLENGE` stays `Pending` (logged); `FAILED`/`CANCELED` → payment and subscription `Expire`; `REFUNDED` → payment `Refund`, `needsRefund = false`, and a still-`Success` subscription becomes `Dibatalkan` (tier re-evaluated with `renewWindow: false`, customer notified). A payment arriving after the order is `Expire`/`Dibatalkan` is recorded `Success` with `needsRefund = true` and `notifyAdmins`; the subscription isn't revived. **Pricing:** each discount is rounded down to a whole rupiah and the total is computed from the rounded parts; a total of 0 skips the gateway and is paid at once with `payment.method = "FREE"` (`doneOnline` true). **Slots:** `Order.serviceDate` is snapshotted from the schedule at checkout (schema change). `Mingguan`/`Bulanan` may start in the past (only published slots after today are taken). Slots move `Terjadwal → Disiapkan` `SLOT_PREPARATION_LEAD_MINUTES` (config constant, default 180) before their meal time, in a job every 15 minutes plus a catch-up at worker start. **Snap session** lives in Redis (`Cache`, keyed by payment id, expiring with the order). **Worker:** `createApp` splits into `createModules(deps)` + the Express part, and the worker reuses `createModules`.
- **Slot audit & obstacles:** every `order.status` change **must** insert an `order_status_history` row in the same transaction (`changedById = null` for system/worker changes). **Admin corrections** (UC-27, forward-only, or to `Dilewati` from `Terjadwal`/`Disiapkan` with the note also written as `skipReason`; decided 2026-11-06) must carry a reason in `adminNote` (decided 2026-11-02); the API body field is also `adminNote`. Normal flow changes leave it `null`. Courier/admin obstacle notes go in `delivery_obstacle` and trigger a customer-level notification; the status never changes.
- **Notifications (BR-27):** customer-level goes to `Notification.userId`; package/global/schedule go to `Announcement.scope` (`PACKAGE` with `packageId`, `GLOBAL`, or `SCHEDULE` with `menuScheduleId` for a single service day, e.g. a BR-26 menu change). Delivered through SSE. **How other modules notify people** (decided 2026-11-06): `NotificationsService.notifyUser({ userId, title, body })`, `notifyAdmins({ title, body })` (one row per active `ADMIN`) and `announce({ scope, packageId?, menuScheduleId?, title, body })`, each behind a small interface the caller declares. The row is saved first, then the event is published **after the write, best-effort**: a failed publish is logged as a warning and the call still succeeds (no replay; clients refetch). **Recipients are active users only** (decided 2026-11-06): `GLOBAL` goes to the `CUSTOMER` role (`{ roles: ["CUSTOMER"] }`, so ids are never loaded), `PACKAGE` to customers with a `Success` subscription on the package whose `endDate` is today or later, `SCHEDULE` to customers with a `Success` subscription and a non-`Dilewati` slot on the schedule; orders owns both directions of that rule (the live send and `GET /me/announcements`), so they can't drift apart. `POST /admin/notifications/broadcast` with target `CUSTOMER` only reaches active customers; any other `userId` (staff, inactive, unknown) answers the same 404 `TARGET_NOT_FOUND`. Bodies are trimmed and limited to 2000 characters (titles 150). `PATCH /admin/announcements/{id}` checks the scope on the merged result and never re-sends. Per-user read state for announcements is not built (UC-42 should-have).
- **Backend is the source of truth** for prices, discounts, fees, cut-offs, and status transitions. Historical orders keep their prices when master data changes.
