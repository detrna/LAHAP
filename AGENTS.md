## Key Mathematical Formulas

1. **Daily Production (ToCook):**
   $$\text{TotalPortions}(P, M, D, W) = \sum [\text{order.slot} \mid \text{Success} \land \neg\text{Skipped}]$$
   $$\text{IngredientRequirement}(B, D, W) = \sum_M (\text{TotalPortions}(M) \times \text{QuantityPerPortion}(B, M))$$
2. **Stock Shortage:**
   $$\text{NeedsPurchase}(B) = \max(0, \text{WeeklyRequirement}(B) - \text{CurrentStock}(B))$$
3. **Allergen Clash:**
   $$\text{IsClash} = (\text{UserAllergies} \cap \text{MenuAllergenTags}) \ne \emptyset$$
4. **Order Total (BR-17/18):** `Total = slots × price − tierDiscount − promoDiscount + deliveredSlots × feePerSlot`. Tier is applied first, then promo on the reduced food subtotal. If `promoCode.allowStackWithTier = false`, apply only `max(tier, promo)`. Delivery fees are **never** discounted. **Snapshot the whole breakdown on `Subscription` at checkout** (decided 2026-11-02): `pricePerPortion`, `foodSubtotal`, `tierId` + `tierDiscount`, `promoDiscount`, `deliveryFeePerSlot`, `deliveryFeeTotal`, and `totalPrice` (must equal `foodSubtotal − tierDiscount − promoDiscount + deliveryFeeTotal`). Income reports (UC-31) sum these from `Success` orders, and skips never change them (BR-11).
5. **Delivery Fee (BR-15):** `km = ceil(getDistanceInKm(business, orderPin))`; fee = `0` if `km ≤ freeRadius`, else `(km − freeRadius) × pricePerKm`. Beyond max distance, hide the delivery option (do not reject). The kitchen location is on `Business`. Each parameter resolves as `package.<param> ?? business.<param>`. Snapshot the fee into the order at checkout, because rate changes only apply to new orders (BR-16). `getDistanceInKm` in `backend/src/shared/utils/distance/` returns **unrounded** km, so callers apply `ceil`.
6. **Churn (BR-28):** has a `Success` history ∧ no active order ∧ `MAX(endDate) < today − 14 days`.
7. **Cut-off (BR-09):** order and cancel allowed until 23:59:59 the day before the first service day, in `Asia/Jakarta`.

## Backend Conventions

### Layout (ports & adapters)

| Concern | Location & naming |
| :--- | :--- |
| Port (interface) | `src/shared/ports/<name>/<name>.ts` exporting an interface + I/O types, with `export * from "./errors.js"` at the top |
| Port errors | `src/shared/ports/<name>/errors.ts` |
| Adapter | `src/infrastructure/<port-name>/<vendor>/<vendor>.ts`, class `<Vendor><PortName> implements <PortName>` (e.g. `MidtransPaymentGateway`, `QwenStockLevelEstimator`). Async setup uses a `load<Thing>()` factory |

| Config | `src/config/<name>.ts` exports `<name>EnvSchema` (Zod), `type <Name>Env`, a `readonly` `<Name>Config` interface with **UPPER_SNAKE** keys, `to<Name>Config(env)`, `load<Name>Config(env)` |
| Wiring | Register new config in `config/index.ts` (`Config`, `envSchema`, `loadConfig`), new adapters in `infrastructure/index.ts` (`Adapters`, `createAdapters`). `Adapters` holds adapter instances typed by their ports, and is distinct from the `infrastructure/` folder, which also holds non-port code (`db.ts`, migrations, BullMQ). `db` is deliberately **not** in `Adapters`, so only repository adapters can reach it, and new env vars in `backend/.env.example` |
| Pure helpers | `src/shared/utils/<name>/` with their own `errors.ts` (`decimal/` has `roundHalfUp`). **Shared helpers** (decided 2026-11-05): time in `src/shared/time/` (`timestamp.ts`: `toDbTimestamp`/`toIsoTimestamp`/`fromIsoTimestamp`; `schemas.ts`: `isoTimestampSchema` (offset required) and `isoDateSchema` → `PlainDate`; `calendar.ts`: `startOfWeek`, `nextMonday`, `startOfMonth`/`endOfMonth`, `daysBetween`, `isMonday`, `isFirstOfMonth`; `date-range.ts`: `resolveDateRange(input, { defaultFrom, defaultSpanDays, maxDays })`, whose defaults come from the service's clock); meal times in `src/shared/utils/meal-time/` (`clockTimeSchema` for `HH:mm` input, `toDbTime`, `isSameClockTime` at minute precision); request Zod helpers in **`src/shared/schema/`** (same name as the modules' `schema/`): `queryBooleanSchema`, `searchQuerySchema`, `uniqueArray(item, { by? })`, `decimalSchema({ scale, min?, max?, exclusiveMin? })`, `latitudeSchema`/`longitudeSchema` + `refineCoordinatesTogether`, `photoKeySchema`; photo URLs in `src/shared/media/photo.ts` (`toPhotoUrl`, `toPhotoUrls`, which signs each distinct key once) |
| Domain modules | `src/modules/<module>/` (decided 2026-11-03, plural names), **one folder per layer, with a class file + one file per method** (Go-style receivers; see the block below the table): `controller/<module>.controller.ts`: class `<X>Controller` (HTTP only: validated input → service → `createSuccessResponse`), with handlers in `controller/<action>.ts`. `service/<module>.service.ts`: class `<X>Service` (use cases and business rules; UML anemic domain, so the logic lives here), with methods in `service/<action>.ts`. `service/interfaces/<module>.repository.ts`: the repository **port the service owns** (interface `<X>Repository` + record types, re-exports the domain errors). `repository/prisma/<module>-repository.ts`: class `Prisma<X>Repository implements <X>Repository`, with methods in `repository/prisma/<action>.ts`. `domain/`: `errors.ts` (single file) and `<entity>.domain.ts`, which holds the module's **response types mirroring the `openapi.json` schemas** (decided 2026-11-03: one `readonly` interface per schema with the same name, nullable = `T | null`, not required = `foo?: T | undefined`, dates as ISO strings; enum schemas as `<NAME>S` const arrays + a type, like `ROLES`) plus pure rules. Request schemas (`*Create`, `*Update`, `*Request`) are not domain types; they go in `schema/` as Zod. Another module's domain types may be imported with `import type` only. Shared shapes live in `shared/` (`Role`, `MealTimeView`, `BatchDeleteResult`/`BulkUpdateResult`). `routes/<module>.routes.ts` (single file): `create<X>Router({ controller, tokenProvider })`, where each endpoint chains authenticate → authorize(`x-roles`) → validate → `controller.<handler>`. `schema/<module>.schemas.ts`: Zod request schemas mirroring `openapi.json`. `container/<module>.container.ts`: class `<X>Container({ db, adapters, http, …otherServices })` (`ModuleDeps` in `src/modules/module-deps.ts`) builds repository → service → controller → router, exposes `service` + `router`, wiring only. The container is the only place that sees the whole `adapters` object: it hands services and routers **individual ports** (`new UsersService(repo, adapters.hasher)`), never `adapters` itself. **Dependency rule:** `service/` and `domain/` never import `repository/prisma/`, Prisma, Express or `infrastructure/`. Only the container (the composition root) imports the adapter, and the adapter imports the port (outer → inner). Tests sit next to each method file. **Interfaces only at boundaries:** the repository port, plus **cross-module** dependencies, which are declared by the *consuming* module in `service/interfaces/` (e.g. orders declares `TierDiscountProvider`, and `TiersService` satisfies it structurally). No interface between controller and service; tests mock the class type (`Pick<UsersService, "getById">`), which works because dependencies are `readonly`, not `private`. `app.ts` creates containers in dependency order, passes **services** (never repositories) across modules, creates shared singletons once and passes them in, and mounts each `router` on the `/api` router. **Where pure rules live (decided 2026-11-03):** a rule only one module uses goes in that module's `domain/` as its own file + test (`modules/orders/domain/order-total.ts`, `cut-off.ts`, `delivery-fee.ts`; `modules/catalog/domain/package-availability.ts`). It moves to `src/shared/utils/<name>/` only when a second module needs it, because other modules may only `import type` from a module's domain. Shared today: `phone`, `meal-time`, `distance`, `message-template`. **Module boundaries (decided 2026-11-03):** each table has exactly one owning module, and only that module's service writes it. Another module's data, read or write, goes through **its service** behind an interface the consumer declares. A repository never crosses modules. A module's own read models (kitchen to-cook, courier list, reports) may live in its own repository and **read** tables other modules own, but never write them. `orders` owns Subscription, Order, OrderStatusHistory **and Payment** (no separate payments module: checkout, the Midtrans webhook, verify-cash, confirm-refund and the 15-min expiry write both in one transaction). **Every write to `order` goes through `orders`**, so the handlers for `/kitchen/food-ready`, `/kitchen/orders/{id}/alternative-menu`, `/courier/orders/{id}/complete`, `/admin/orders/{id}/complete`, `/admin/orders/{id}/status` and `/admin/courier-assignments` live in the orders router (paths and `x-roles` unchanged), keeping BR-23 and the history insert in one place. `kitchen` keeps to-cook; `delivery` keeps the courier list and obstacles. **Modules** (decided 2026-11-03; all scaffolded, in `app.ts` creation order): `auth` (RefreshToken; register/login/refresh/logout), `users` (User, UserAllergy; `/me`, Admin·Users), `settings` (Business; `GET /business`, Admin·Settings), `files` (`POST /files`, no tables), `realtime` (the SSE hub + `GET /realtime/stream`, no tables), `notifications` (Notification, Announcement), `catalog` (Allergy, Package, Schedule, Menu, ScheduleMenu, MenuIngredient; public catalog, Admin·Catalog, Admin·Schedules), `ingredients` (Ingredient, IngredientAllergy; Admin·Ingredients, `/kitchen/ingredients*`, shopping list, photo estimate), `tiers` (Tier, Membership; `/me/membership`, Admin·Tiers), `promo-codes` (PromoCode; Admin·Promotions), `orders` (see above, plus Admin·Reports), `kitchen` (to-cook, read-only), `delivery` (DeliveryObstacle; courier list, obstacles), `retention` (MessageTemplate; churn). Containers take only `ModuleDeps` until a method needs a cross-module dependency. |

### Errors

- **Where errors live** (decided 2026-11-05): an error several modules use goes in `src/shared/errors/`; an error only one module throws stays in that module's `domain/errors.ts`. Shared today: `AppError`, `ValidationError` (400 `VALIDATION_ERROR` with `issues`; `RequestValidationError` and `InvalidDateRangeError` extend it, and `errorHandler` returns the issues for any of them) and `InvalidStateError` (422 `INVALID_STATE`). Throw `new InvalidStateError("cut-off has passed")` for every business-rule or state violation, with a specific lowercase message, rather than a new class per case.
- Every domain or infra error extends `AppError` (`src/shared/errors/app-error.ts`) with `readonly code` (UPPER_SNAKE string) and `readonly statusCode` (HTTP status).
- Name classes with an `…Error` suffix (`InvalidHashInputError`). The `Error…`-prefixed classes in `stock-level-estimator/errors.ts` are an outlier; don't copy them.
- Messages are lowercase and do not end with a period. Always pass `{ cause }` when wrapping.
- Adapters must translate vendor exceptions into port errors (`…ProviderError` = 502, `…FailureError(operation, cause)` = 500). Never leak vendor errors.
- Constructor misconfiguration throws a plain `Error("<ENV_VAR> is not set")` (fail fast at boot).

### HTTP

- Responses use the envelope helpers in `src/shared/response/`: `createSuccessResponse(data, meta?)` gives `{ data, meta? }`, `createPaginatedResponse(items, {page,limit,total})` gives `{ data, meta: PaginationMeta }`, and errors come out as `{ error: { code, message, issues? } }` (produced only by `errorHandler`).
- Middleware is a factory that takes a deps/options object (`authenticate({ tokenProvider })`, `errorHandler({ logger })`). App-level order in `app.ts`: `trust proxy` setting → `requestLogger` → `helmet` → `corsPolicy` → `express.json` → routers → `errorHandler` (last). Route chain order: `authenticate → authorize(...roles) → rateLimit → uploadImage → validateRequest/validateBody/... → paginate() → handler` (skip the ones a route doesn't need).
- **HTTP foundation** (decided 2026-11-03; settings in `config/http.ts`, reached through `ModuleDeps.http`):
  - `requestLogger({ logger })`: `req.id` from a safe incoming `X-Request-Id`, otherwise a UUID, echoed in the response header. It logs one `request completed` line per request (`requestId, method, path, statusCode, durationMs, userId?`). The path is logged without the query string, so tokens never reach the logs, and `/health` is skipped. `errorHandler` adds `requestId` to its logs.
  - `corsPolicy({ origins })`: allows `CORS_ORIGINS` (exact origins, comma-separated) **with credentials** (needed for the refresh cookie; never use `*`), and exposes `X-Request-Id` and `Retry-After`. Set `TRUST_PROXY` when deployed behind a reverse proxy, so `req.ip` is the client.
  - `uploadImage({ field, maxBytes: http.UPLOAD_MAX_BYTES })` (multer, memory storage): one JPEG, PNG or WebP per request. The type is detected from the file's magic bytes, and `req.file.mimetype` is overwritten with it. Failures: missing file → 400 `VALIDATION_ERROR`, too large → 413 `PAYLOAD_TOO_LARGE`, other types → 415 `UNSUPPORTED_MEDIA_TYPE`. Used by `POST /files` (`field: "file"`) and the photo estimate (`field: "image"`). Put `validateBody` after it for the text fields.
  - `rateLimit({ cache, logger, name, limit, windowSeconds, key? })`: a fixed window per client IP, on `Cache.increment`. Over the limit it sets `Retry-After` and returns 429 `TOO_MANY_REQUESTS`. When Redis fails it lets the request through and logs a warning. Applied to `POST /auth/login` and `POST /auth/register` with `AUTH_RATE_LIMIT_MAX`/`AUTH_RATE_LIMIT_WINDOW_SECONDS` (default 10 per 60 s).
- Never write error responses yourself. Async route handlers just `throw` (or let promises reject): Express 5 forwards that to `errorHandler`. Middleware forwards failures with `next(err)`.
- **Request schemas reuse the shared helpers** (`src/shared/schema/`, `shared/time/schemas.ts`, `clockTimeSchema`): boolean query filters use `queryBooleanSchema`, **never `z.coerce.boolean()`** (it turns `"false"` into `true`); `?search=` uses `searchQuerySchema` (an empty value means no filter); dates use `isoDateSchema`, timestamps `isoTimestampSchema`, meal times `clockTimeSchema`; money, distances and percentages use `decimalSchema` with the column's scale and limits (e.g. `Numeric(5, 2)` → `max: 999.99`), so out-of-range input is a 400 rather than a database 500; id lists use `uniqueArray(z.uuid())`.
- Validated, coerced input replaces `req.body/query/params`. `req.user = { userId, name, role }` and `req.pagination = { page, limit, offset, skip, take }`.
- **Auth sessions (decided 2026-11-02, refresh tokens stored 2026-11-04): JWT pair, stateless access token, stored refresh token.** Register/login return `{ accessToken, refreshToken, tokenType: "Bearer", expiresIn, refreshExpiresIn, user }` (`JwtTokenProvider.signTokenPair`, whose `refreshTokenId` is the refresh token's `jti`). Access tokens are never stored or looked up (they stay valid until they expire). Every issued refresh token gets a `refresh_token` row (`id` = `jti`, `expiresAt`, `revokedAt`), owned by `auth` (`AuthRepository`). `POST /auth/refresh` **rotates**: it revokes the presented token with a conditional update (`revokedAt IS NULL`, so two concurrent refreshes can't both win), re-checks the user still exists and `isActive`, and issues a new pair. A token that is stored but already revoked counts as **reuse** (likely theft): every active token of that user is revoked and 401 `INVALID_TOKEN` (`refresh token has been revoked`). Two tabs refreshing with the same token at once can trigger it. A token with no row (unknown `jti`) is just 401. `POST /auth/logout` is **public** (no access token, so it works after the access token expired): it revokes the refresh token from the body or cookie and always answers 204, also with no token, an invalid or expired one, or one that is already revoked (logout never triggers reuse detection). There's no "log out everywhere" endpoint yet; `revokeRefreshTokensOfUser` already exists for it. Expired rows are never cleaned up yet (a worker job can delete by `expiresAt` later).
- **Refresh cookie (decided 2026-11-04):** register, login and refresh also set the refresh token as an `HttpOnly` cookie (`AUTH_COOKIE_NAME`, default `lahap_refresh`; `Path=/api/auth`; `Max-Age` = `refreshExpiresIn`), and logout clears it with the same attributes (`controller/refresh-cookie.ts`). The frontend and backend run on **different sites**, so production uses `AUTH_COOKIE_SAME_SITE=none` + `AUTH_COOKIE_SECURE=true` (config refuses `none` without `Secure`); local development uses `lax`/`false`. The refresh token **also stays in the response body** (decided 2026-11-04: sending it in the body is standard for OAuth and native clients), and `/auth/refresh` and `/auth/logout` read the body first, then the cookie (`readRefreshToken`; `cookieParser()` on those two routes only). Refresh answers 401 `MISSING_TOKEN` when neither is sent. Browsers should rely on the cookie (`credentials: "include"`) and keep only the access token in memory. Cross-site cookies can be blocked by Safari and third-party-cookie restrictions; the body token is the fallback. A leaked refresh token works only until it or its successor is used again (reuse detection) or the user logs out; otherwise it expires after `JWT_REFRESH_EXPIRES_IN` (7d).
- **Auth implementation** (decided 2026-11-03):
  - Each token carries `typ` (`access`/`refresh`), checked on verify. `JwtTokenProvider` refuses to start when `JWT_SECRET` equals `JWT_REFRESH_SECRET`. `TokenPair.expiresIn` and `refreshExpiresIn` are the access and refresh tokens' lifetimes in seconds.
  - `users` owns passwords: `UsersService.registerCustomer`/`verifyCredentials`/`getActiveById` hash and compare through the `Hasher`, and the hash never leaves the module. `auth` reaches them through its own `UserAccounts` interface, and `app.ts` creates `users` before `auth`.
  - Login gives the same 401 `INVALID_CREDENTIALS` for an unknown user, a wrong password, an inactive account and an unparseable identifier, and runs one bcrypt compare (against a dummy hash) even when the user doesn't exist. An identifier containing `@` is an email (lowercased); anything else goes through `normalizePhone`.
  - Register: 409 `CONFLICT` (`phone is already registered` / `email …`, including concurrent sign-ups that hit the unique constraint), 400 `UNKNOWN_ALLERGY` for ids not in the allergy list. Request bodies use `phoneSchema`, and passwords are 8–72 characters **and** at most 72 bytes (bcrypt's limit).
  - `AuthSession.user` is `User` with `allergies` and without `membership`/`isChurned`; `/me` returns the full profile.
- **Media (decided 2026-11-02): no File table.** `POST /files` (multipart) uploads through `ObjectStorage` and returns `{ key, url }`. Clients send the `key` as `photoKey` when creating or updating an entity. Every response exposes `photoUrl = getSignedUrl(photoKey)`, signed fresh on each read, because the adapter only issues expiring signed URLs (`S3_SIGNED_URL_EXPIRES_IN`). Never store URLs. Uploads that are never attached stay in the bucket (acceptable for the MVP).
- The API prefix is `/api/...`. **`docs/api/openapi.json` supersedes the USE_CASES §5 route map** (decided 2026-11-02). Its conventions:
  - Paths use the code's model names: `/subscriptions` = PRD "Pesanan", `/orders` = slots. Role areas are `/kitchen/*`, `/courier/*` and `/admin/*`; the signed-in user is `/me/*`; public catalog routes are `/packages`, `/allergies` and `/business`.
  - Each operation lists its allowed roles in `x-roles`.
  - Status codes: 409 for uniqueness or "still referenced" conflicts; **422 `INVALID_STATE`** for business-rule or state violations (cut-off passed, wrong slot status, unavailable package); 404 also for other users' resources.
  - Checkout (`POST /subscriptions`, with `/subscriptions/preview` for the dry run) takes `menuScheduleIds` for `Harian`, or `periodStart` + `deliveryTimes` for `Mingguan`/`Bulanan`.
  - An invalid promo code never fails the request; it comes back in `preview.promo.reason`.
  - Bulk endpoints (`/admin/courier-assignments`, `/admin/menu-schedules/publish`, `/kitchen/food-ready`) accept explicit ids **or** a group (date + meal time, package + date range, schedule). The data is still written per row.
  - Realtime is one SSE stream, `GET /api/realtime/stream`, with events `slot.status`, `slot.obstacle`, `slot.menu`, `notification` and `announcement`. Because `EventSource` can't send headers, it also accepts `?accessToken=`.

### TypeScript & style

- ESM with `nodenext`: relative imports **must end in `.js`**. Use `import type` for type-only imports (`verbatimModuleSyntax`).
- `exactOptionalPropertyTypes` is on, so optional props are written `foo?: T | undefined`. Build conditional objects with `...(x !== undefined ? { x } : {})`. `noUncheckedIndexedAccess` is on.
- Interface fields are `readonly`. Prefer `interface` for shapes and Zod for runtime validation of anything external (env, request, LLM output, decoded tokens).
- Prettier: 4 spaces, 120 cols, double quotes, semicolons, trailing commas, `arrowParens: "avoid"`. Organize imports on save.
- Format with `npm run format` (from `backend/`); `npm run format:check` only reports and is required by CI. Both read the root `.prettierignore` (generated contract files, migrations) and `backend/.gitignore`.
- **No comments in code you write** (decided 2026-11-04), in any file: no `//` lines, no `/** … */` doc comments (ports and middleware included), no commented-out code. This also applies to tests, config, migrations and scripts. Names, types and tests carry the meaning. Comments already in the code stay on lines you don't change; don't add new ones next to them.

### Database (Prisma 8, contract-first)

- This is **Prisma 8 (`@prisma/orm-postgres`)**, not `@prisma/client`/`schema.prisma`. Read `backend/.claude/skills/prisma-8/SKILL.md` and its references before any DB work; training-data Prisma knowledge is wrong here.
- Source of truth: `src/infrastructure/database/prisma/contract.prisma` → `npm run contract:emit` regenerates `contract.json`/`contract.d.ts` (do not hand-edit, and don't format them). Migrations live in `.../prisma/migrations/app/<YYYYMMDDTHHMM>_<name>/`.
- CI fails when `contract.json`/`contract.d.ts` weren't re-emitted after a `contract.prisma` change (`static` job), and when the contract has a change no migration covers (`prisma db verify` in the `integration` job), so commit the emitted files and the migration together with the contract change.
- Queries: `db.orm.public.<Model>.create(...)`, `.where({...}).update(...)`. `Db` comes from `infrastructure/database/prisma/db.ts`.
- Repositories implement a port: the module's `<module>.repository.ts` for domain modules, `shared/ports/<x>-repository/` for infra (`JobRunRepository`). Domain-module adapters live **inside the module** (`src/modules/<module>/repository/prisma/`, class file + one file per method). Infra repositories stay in `infrastructure/database/prisma/<x>-repository.ts`. Both are named `Prisma<X>Repository`, map rows with `to<X>Record`, and wrap failures in `<X>RepositoryFailureError(operation, cause)` (rethrow NotFound errors as-is). Map a unique violation to the domain's conflict error with `getUniqueViolationConstraint(error)` (`infrastructure/database/prisma/sql-errors.ts`, returns the constraint name, e.g. `user_phone_key`), and a foreign key violation (a Restrict FK hit by a racing delete, or a write referencing a missing id) with `getForeignKeyViolationConstraint(error)` (e.g. `menu_ingredient_ingredient_id_fkey`). Read `Numeric` columns with `fromNumeric`/`fromNumericOrNull` and write them with `toNumeric(value, scale)`/`toNumericOrNull` (`prisma/numeric.ts`, half-up rounding to the column's scale). Every `ilike` search goes through `toContainsPattern(term)` (`prisma/like.ts`), which escapes `%`, `_` and `\` so they match literally. The ORM brands `VarChar` columns: `where({ id })` accepts plain strings, but `.in([...])` needs `ids as Varchar<36>[]` (`import type { Varchar } from "@prisma/orm-postgres/contract-builder"`). `Numeric` columns come back as strings, so convert them to numbers in `to<X>Record`.
- **Seeder** (decided 2026-11-03): `npm run seed` (add `-- --reset` to truncate every domain table first). `src/infrastructure/database/prisma/seed/main.ts` runs the modules in `seed/modules/<area>/` (`<area>.data.ts` fixtures + `<area>.seed.ts`) in FK order inside one transaction. Rows have fixed ids (`seedId()`) and are upserted, and link tables are replaced per parent, so re-runs are idempotent. Schedules cover today + 35 published days + 7 draft days (Asia/Jakarta), so rerun it before a demo. Fixtures follow the official PRD examples (Paket Hemat Rp15.000 / Reguler Rp20.000, tiers Biasa/Silver/Gold, `MERDEKA`, Malang delivery defaults); every account uses password `password123`. It refuses to run when `IS_PRODUCTION=true`. Subscriptions, orders and payments are not seeded until checkout exists (their price snapshots must come from the real calculation).
- Schema conventions: ids `VarChar(36) @id @onCreate(uuid())`, camelCase fields with `@map("snake_case")`, singular `@@map("table")`, money `Numeric(12, 2)`, coordinates `Numeric(10,8)`/`Numeric(11,8)`. Derived labels (`Akan Datang`/`Aktif`/`Selesai`, fees) are computed, never stored. **Mutable entities carry `createdAt` + `updatedAt`** (`@onUpdate(now())`, decided 2026-11-02). Link tables and append-only logs (`OrderStatusHistory`, `DeliveryObstacle`, `JobRun`) have no `updatedAt`. **Photo columns are `photoKey`** (object-storage key, e.g. `menus/2026/11/<uuid>.webp`), never URLs.

### Time (decided 2026-11-03)

- **Never read the system clock in services or domain code** (`Temporal.Now`, `new Date()`, `Date.now()`). Take a `Clock` (`src/shared/ports/clock/`, `adapters.clock` = `SystemClock`). `clock.now()` returns a `Temporal.ZonedDateTime` in `BUSINESS_TIME_ZONE` (`src/shared/time/time-zone.ts`, `Asia/Jakarta`), whatever the server's zone. Tests use `createFixedClock(...)`.
- **Domain `Timestamp` columns store UTC wall-clock time** (`Temporal.PlainDateTime`), because that's what Prisma's `@onCreate(now())`/`@onUpdate(now())` write. When writing a timestamp yourself, use `toDbTimestamp(clock.now())` from `src/shared/time/timestamp.ts`. `Date` columns are business dates: "today" is `clock.now().toPlainDate()`. `JobRun` keeps `TimestamptzJsDate` (infra-only, absolute instants).
- **Responses render timestamps in Asia/Jakarta with the offset and milliseconds** (decided 2026-11-03): `toIsoTimestamp(row.createdAt)` gives `2026-11-03T08:00:00.000+07:00`. Never send a raw `PlainDateTime`. Factory examples use the same form.

### Deployment (decided 2026-11-05)

- **Target:** one VPS reached over SSH, running everything with Docker Compose. A green push to `main` runs, after `static`, `unit` and `integration`: `build-and-push` (builds `backend/Dockerfile` and pushes `ghcr.io/<owner>/${{ vars.IMAGE_NAME }}` tagged `sha-<commit>` and `latest`, with the built-in `GITHUB_TOKEN`), then `deploy` (GitHub environment `production`, never cancelled midway). PRs never deploy.
- **The deploy job:** copies `backend/docker-compose.yml` to `$HOME/<repo>/docker-compose.yml` on the server (`appleboy/scp-action`, so the server always runs the committed file), then over SSH: stops if `.env` is missing, logs in to GHCR with the run's own `GITHUB_TOKEN` (`packages: read`, valid only while the job runs; logged out again however the script ends), pulls `api` and `worker`, runs `docker compose run --rm api npx prisma db migrate`, then `docker compose up -d --wait --remove-orphans` (waits for the API healthcheck) and `docker image prune -f`. **Never edit the compose file on the server**: the next deploy overwrites it. Roll back by redeploying an older `sha-<commit>` tag (`IMAGE_TAG=sha-<commit> COMPOSE_PROFILES=app docker compose up -d` on the server, with a migration that still fits that version).
- **Production build:** `npm run build` (`tsc -p tsconfig.build.json` into `dist/`, without tests, `test-utils`, migrations or the seeder), `npm start` (API) and `npm run start:worker`. Production runs plain `node`, never `tsx`. The image is multi-stage on `node:26.13-slim` (keep it equal to `.nvmrc`), runs as the non-root `node` user, and holds `dist/`, the production `node_modules`, `prisma.config.ts` and `src/infrastructure/database/prisma/` (contract + migrations). The `prisma` CLI is a production dependency because migrations run from the image.
- **Compose:** `api` and `worker` (the same image; the worker runs `node dist/worker.js`) sit in the `app` profile, so a plain `docker compose up -d` still starts only Postgres, Redis and SeaweedFS (local development and CI). `docker compose --profile app up --build` runs the whole stack locally; the server uses `COMPOSE_PROFILES=app`. Inside Docker, `DB_URL` and `REDIS_URL` are overridden to the `postgres` and `redis` service names, so one `.env` works for `npm run dev` and for the containers. Logs go to the `app_logs` volume (`log/api.txt`, `log/worker.txt`). **Every port is bound to `127.0.0.1`**: only a reverse proxy on the host (nginx or Caddy, with HTTPS) exposes the API port and the S3 port; Postgres, Redis and the SeaweedFS UIs are never public.
- **Production `.env`** lives only on the server, at `$HOME/<repo>/.env` (`chmod 600`), created and edited by hand, never in the repo or in GitHub. When a change adds a variable to `.env.example`, add it to the server's `.env` before deploying it. It must set at least: `IS_PRODUCTION=true`; strong, different `JWT_SECRET` and `JWT_REFRESH_SECRET`; `AUTH_COOKIE_SAME_SITE=none` and `AUTH_COOKIE_SECURE=true`; `CORS_ORIGINS` (the frontend origin); `TRUST_PROXY` (behind the reverse proxy); `DB_*`, `S3_*` and the vendor keys. `S3_ENDPOINT` must be the **public** HTTPS address of the S3 port, because photo URLs are signed with it (so it isn't overridden in compose). For the same reason, running the app profile locally needs an `S3_ENDPOINT` reachable from inside the containers.
- **GitHub settings:** repository secrets `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY` (a deploy-only private key), `VPS_PORT` and `VPS_SSH_FINGERPRINT` (`ssh-keyscan -p <port> <host> | ssh-keygen -lf -`; without it the server's identity isn't checked); repository variable `IMAGE_NAME` (lowercase, `lahap-backend`). The deploy job runs in the `production` environment. The GitHub repository is `detrna/LAHAP`, so the server folder is `$HOME/LAHAP` (case-sensitive).
- **Server setup (once):** Docker with the compose plugin, a deploy user in the `docker` group with the deploy key, the `$HOME/<repo>/` folder with `.env`, and the reverse proxy. Keep a few GB free: SeaweedFS stops accepting files when the disk is about 99% full.

## Domain Quick Reference

- **Roles:** Customer, Admin (owner), Kitchen, Courier. One `/login` page with role-based redirect. **Stored values** (decided 2026-11-02): `CUSTOMER`, `ADMIN`, `KITCHEN`, `COURIER` (UPPER_SNAKE, case-sensitive). Use `ROLES`/`Role`/`isRole` from `src/shared/auth/roles.ts`. The token port, the JWT adapter (`z.enum(ROLES)`, so unknown roles are rejected) and `authorize(...roles: Role[])` are all typed with it. Tests use only these four.
- **Terminology trap:** in the PRD, **"Pesanan"/order means the `Subscription` entity** (it carries `Pending`/`Success`/`Expire`/`Dibatalkan`), while **"Slot" is the `Order` model**. "Jadwal Menu"/`MenuSchedule` (UML) is the `Schedule` model. So rules worded "pesanan …" (BR-13, BR-21, BR-22) apply to `subscription`, not to the `order` table.
- **Slot = 1 `Order` row = 1 portion = 1 delivery**, unique `(subscriptionId, menuScheduleId)`. Delivery vs pickup is stored once on `subscription.isDelivery` and applies to every slot (BR-13).
- **Allergy note & skip reason** (decided 2026-11-02): `user.allergyNote` holds free-text allergies outside the list (UC-41). It can't be matched to menu tags, so **any customer with a non-empty note has all their slots shown in the kitchen's special category** (UC-39), alongside notes and tag clashes. `order.skipReason` is optional and only set when status becomes `Dilewati` (UC-44). "Skip Hari Ini" writes the same reason to each skipped slot.
- **Churn follow-up templates** (decided 2026-11-02): admin-written templates live in `MessageTemplate` (`name`, `body`). Placeholders are a **fixed map in code**: `MESSAGE_PLACEHOLDERS` in `src/shared/utils/message-template/` (`name` → `{nama}`, `lastPackage` → `{paket_terakhir}`, `endDate` → `{tanggal_berakhir}`, `daysSinceLastOrder` → `{lama_tidak_memesan}`, `promoCode` → `{kode_promo}`). Call `generateMessage(template.body, { name, promoCode, … })`, then URL-encode the result into `https://wa.me/<62…>?text=…`. To add a placeholder, add it to that map, never to the database.
- **Courier assignment** (decided 2026-11-02): the admin assigns a courier **per slot** via `order.courierId`. There are no shift tables. A courier's to-do list (UC-30) is their slots where `courierId = me`, `subscription.isDelivery`, and status `Diantar` (or earlier, for the day's list). The admin UI may bulk-assign, but the data stays per slot.
- **Registration & identity** (decided 2026-11-02): only `phone` + password are required (UC-01). Normalize `phone` with `normalizePhone()` from `src/shared/utils/phone/` before saving **or** looking it up: digits starting with `62` (`0812…`/`+62812…`/`812…` → `62812…`; anything else is 400 `INVALID_PHONE_NUMBER`). `email` is optional (`String?`, unique), stored trimmed and lowercased. When no name is given, set `name = phone`, so `User.name` and the token's `sub.name` are never empty. Login accepts phone or email (UC-13).
- **Order period** (decided 2026-11-02): `package.periods` (`String[]`) lists the periods a package offers (`"Harian"` | `"Mingguan"` | `"Bulanan"`, at least one), and `subscription.period` is the customer's choice, which must be in that list. There is no `durationDays` on packages. Order length = `subscription.startDate`/`endDate` (first and last slot date, for every period). The package sales window = `package.startAt`/`endAt`.
- **Changing the delivery method** (decided 2026-11-02, follows the official PRD): the **MVP has no in-app switch**. The customer cancels before cut-off (manual refund, UC-43) and re-orders (BR-13, UC-08 point 8). Post-release (§7.5): delivery → pick-up **refunds** the delivery fee for the remaining slots, and pick-up → delivery pays the extra fee as a `payment.type = "DELIVERY_SERVICE_UPGRADE"` payment. That value is reserved, and the MVP only creates `"SUBSCRIPTION"`. Building it then will need per-slot method history again (see the issue-13 discussion).
- **Online/Offline & payment method** (decided 2026-11-02): `subscription.purchaseType` is `"Online"` (gateway only, never cash) or `"Offline"` (gateway or cash), set once at checkout (UC-03). `payment.method` is `"CASH"`, `"MIDTRANS"` (channel not chosen yet), or `"MIDTRANS_<PAYMENT_TYPE>"` once the webhook reports it. There is **no `doneOnline` column**. API responses for payments must include a derived `doneOnline = method !== "CASH"`.
- **Each order has its own recipient and delivery point** (decided 2026-11-02). At checkout, save `recipientName` (always), and `deliveryAddress`, `deliveryLatitude`/`deliveryLongitude` and `deliveryDistanceKm` (required when `isDelivery`) on `Subscription`. `User.address`/`latitude`/`longitude` only **prefill** the checkout form and are never written by checkout. Courier contact uses `user.phone`.
- **Meal times (decided 2026-11-02):** the admin types each package's meal times into `Package.deliveryTimes` (`Time[]`, minute precision). There is no meal-time table. A slot is package + date + meal time: `Schedule.deliveryTime`, unique on `(packageId, date, deliveryTime)` (BR-07). The app must check that the time is in the package's list, and refuse to remove a time that slots of active orders still use (UC-20). One subscription can span several meal times (UC-06, UC-09).
- **Meal-time range label is derived, never stored:** use `toMealTimeView(time)` from `src/shared/utils/meal-time/`, which returns `{ time: "07:00", range: "Pagi" }`. The ranges are Pagi 00:00–10:59, Siang 11:00–15:59, Malam 16:00–23:59. It accepts `"HH:mm[:ss]"` strings or `Temporal.PlainTime`, which is what Prisma returns for `Time` columns (Node ≥ 26.8.2 has `Temporal` built in; the project runs 26.12. Its types come from TypeScript's `esnext` lib, set in both tsconfigs, so never import a polyfill).
- **Status values (decided 2026-11-02): Indonesian/PRD naming, stored verbatim and case-sensitive.** Never use the English variants (`SCHEDULED`, `PENDING`, `ACTIVE`, …) for domain statuses. Infra-only statuses such as `JobRun` (`RUNNING`/`SUCCESS`/`FAILED`) are unaffected.
  | Column | Allowed values |
  | :--- | :--- |
  | `subscription.status` | `Pending`, `Success`, `Expire`, `Dibatalkan` |
  | `payment.status` | `Pending`, `Success`, `Expire`, `Refund` |
  | `order.status` (slot) | `Terjadwal`, `Disiapkan`, `Diantar`, `Siap Diambil` (with a space), `Selesai`, `Dilewati` |

  Other enumerated columns (UPPER_SNAKE, decided 2026-11-02): `payment.type` = `SUBSCRIPTION` | `DELIVERY_SERVICE_UPGRADE`; `announcement.scope` = `GLOBAL` | `PACKAGE` | `SCHEDULE`.
- **Subscription lifecycle:** Pending payments expire after 15 min through the worker (BR-20). Only `Success` counts for ToCook, courier lists, revenue, and churn (BR-22). The display labels `Akan Datang`/`Aktif`/`Selesai` are derived from dates.
- **Schedule publication:** `Schedule` (called `MenuSchedule` in UML; FK `order.menuScheduleId`) has **no status column**. Visibility is only `isPublished` (decided 2026-11-02).
- **Slot status flow (BR-23), forward-only:** delivery `Terjadwal → Disiapkan → Diantar → Selesai`; pickup `Terjadwal → Disiapkan → Siap Diambil → Selesai`; skip → `Dilewati` (allowed before food-ready, no refund). Courier obstacles are timestamped **notes + notification, not a status**. Every slot status change must record the actor's `userId` and a timestamp (PRD §9.4).
- **Menus:** 1 primary + at most 1 alternative per schedule (`ScheduleMenu.isPrimary`). `@@unique([scheduleId, isPrimary])` enforces the "at most"; the app must verify a primary exists before setting `schedule.isPublished = true`. `Menu.tags` is `String[]` (Postgres `text[]`, no NULL elements). Allergens are inherited from ingredients (union). A clash warns at checkout but never blocks. The kitchen assigns alternatives manually by setting `order.usesAlternativeMenu = true`. A slot's menu is the schedule's `ScheduleMenu` with `isPrimary = !usesAlternativeMenu`, and ToCook counts primary and alternative portions separately.
- **Loyalty tier = `user.membership`** (decided 2026-11-02): `Membership` is 0..1 per user (`userId` unique) with `tierId`, `startedAt`, `expiresAt = startedAt + tier.durationDays`. Apply the tier discount only while `expiresAt > now`. Re-evaluation updates the row in place (no history), and there is no `User.tierId`.
- **Deleting a tier** (UC-38, decided 2026-11-02): `Membership.tier` blocks deletion while members exist. In one transaction: move its members to the **previous tier** (the highest `requiredSubscriptionDays` below it, which is unique), **keeping `startedAt`/`expiresAt`**. If there's no lower tier, delete those memberships. Then delete the tier. Subscriptions that used it get `tierId = null` and keep `tierDiscount`. Validate UC-36: `requiredSubscriptionDays ≥ 0`, `durationDays > 0`, `0 ≤ discountPercent ≤ 100`.
- **Business (singleton):** exactly one `business` row holds the kitchen location, delivery defaults, `paymentTimeoutMinutes` (BR-20) and `whatsappNumber` (the business contact number, kept for future features; churn `wa.me` links use the customer's number). Read it, don't hardcode these values. The admin `/api/admin/settings` endpoint (USE_CASES §5) edits this row. Tenant scoping (`business_id` everywhere) is **deferred past the MVP** (decided 2026-11-02); don't add `businessId` columns.
- **Packages:** a package is **active** (derived, never stored) when `isActive && startAt ≤ now && (endAt == null || now < endAt)` (BR-03, UC-22). `isActive` is the admin's reversible manual switch, and `endAt = null` means no expiry. Only active packages appear to customers and accept new orders. Running `Success` orders on an inactive package are still served (kitchen, courier, slots ignore it).
- **Promo codes:** `discountType` is `"Persen"` | `"Nominal"`, and `discountValue` is a percent or Rp accordingly. Enforce `minPurchase` against the food subtotal before discounts. Also check `quota`, `validUntil` and `isActive`.
- **Cancellation & refunds:** cancelling a `Success` subscription sets `status = "Dibatalkan"` and `needsRefund = true`. The admin refunds outside the app, then confirms (`POST /api/admin/payments/:id/confirm-refund`), which sets that payment's `status = "Refund"` and the subscription's `needsRefund = false` in one transaction.
- **Slot audit & obstacles:** every `order.status` change **must** insert an `order_status_history` row in the same transaction (`changedById = null` for system/worker changes). **Admin corrections** (UC-27, forward-only) must carry a reason in `adminNote` (decided 2026-11-02); the API body field is also `adminNote`. Normal flow changes leave it `null`. Courier/admin obstacle notes go in `delivery_obstacle` and trigger a customer-level notification; the status never changes.
- **Notifications (BR-27):** customer-level goes to `Notification.userId`; package/global/schedule go to `Announcement.scope` (`PACKAGE` with `packageId`, `GLOBAL`, or `SCHEDULE` with `menuScheduleId` for a single service day, e.g. a BR-26 menu change). Delivered through SSE.
- **Backend is the source of truth** for prices, discounts, fees, cut-offs, and status transitions. Historical orders keep their prices when master data changes.

## Open Decisions / Known Inconsistencies

Resolve with the user before relying on any of these. Once one is settled, record the answer here and delete the item.

1. **Gateway → stored payment status mapping.** The `PaymentGateway` port normalizes Midtrans to `PAID/PENDING/CHALLENGE/FAILED/EXPIRED/CANCELED/REFUNDED` (gateway vocabulary, deliberately kept). The obvious mappings are `PAID → Success`, `PENDING → Pending` and `EXPIRED → Expire`. `CHALLENGE`, `FAILED`, `CANCELED` and `REFUNDED` are undecided, so ask before implementing the webhook use case.
2. **Waiting on the PM:** refund flow and receipt OCR are being revised (so the `"Refund"` payment status and the receipt-extractor port may change). Promo-code reuse per customer is still open (official PRD §14.3).
3. **Should-haves deferred until their feature is built:** stock change log with who changed it (UC-40), menu components and cook assignments (UC-34), per-user read status for package/global announcements (UC-42).
